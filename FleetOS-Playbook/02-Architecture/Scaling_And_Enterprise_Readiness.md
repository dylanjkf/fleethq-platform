# Scaling & Enterprise Readiness

## Purpose
Answer one question explicitly, rather than leave it to be re-litigated feature by feature: how does FleetOS support "a fleet of one vehicle or a hundred thousand" (`Core_Principles.md` #10, `CLAUDE.md`) — including a national logistics enterprise with thousands of vehicles, hundreds of concurrent users, and multiple depots — without either (a) requiring a rewrite when that customer signs, or (b) making a five-vehicle courier company pay for infrastructure it doesn't need. This document is the resolution to that tension, arrived at deliberately rather than by default in either direction.

## The model: three tiers, not one big build-out
- **Tier 0 — built now.** Cheap, prevents a future rewrite, adds no new infrastructure to operate.
- **Tier 1 — the seam is designed now; the actual infrastructure is built only when a named, concrete trigger fires.** This is the mechanism that satisfies "scale incrementally so infrastructure grows alongside customer demand" — growth is met when it happens, not provisioned speculatively.
- **Tier 2+ — deferred entirely.** Documented so it's a known future path, not a surprise, but genuinely not built.

Every item below is placed deliberately, not by default — see the reasoning per item.

## What's already correct (no change made here)
These were reviewed against the enterprise requirements and found to already be right:
- **Multi-tenancy**: enforced by real Postgres row-level security (a dedicated low-privilege runtime role, policies keyed on a per-request session setting — see `11-Database/Data_Model.md`), not application-layer filtering. This is already the strongest available answer to "complete data isolation between companies."
- **Horizontal scalability of the app tier**: stateless JWT auth, no in-memory session state, no local file writes anywhere in the codebase — N app instances behind a load balancer already works with zero logic changes.
- **RBAC**: company-defined custom roles with individually grantable permissions, resolved fresh from the database on every request — already exactly what "granular permission-based access control, not fixed roles" asks for (`14-Security/Permissions_Model.md`).
- **International readiness**: Jurisdiction (`08-Compliance/Jurisdiction_Model.md`) and Asset Class (`02-Architecture/Asset_Class_Model.md`) are already independent, first-class axes in the data model — a second country or a second mode of transport is additive by design, not a rewrite.
- **SSO readiness**: `AuthService.issueSessionToken()` is already the single chokepoint every login path funnels through (username/password login, multi-company selection, post-signup auto-login). A future SAML/OIDC identity provider integration is additive — it verifies identity, then calls this same method — not a rewrite of the session model.
- **Zero-downtime deploy discipline**: the additive-then-remove migration pattern (`16-Deployment/Deployment_Overview.md`) was already a stated requirement before this review.

## Tier 0 — implemented
1. **Health checks** (`src/health/`) — `GET /health` (liveness, process-up-at-all, no dependency checks) and `GET /health/ready` (readiness, checks Postgres via `PrismaService`). Deliberately outside the `/v1/` versioning scheme (these are infra endpoints, not the business API contract) and unauthenticated.
2. **Structured (JSON) logging** (`nestjs-pino`, wired in `main.ts`/`app.module.ts`) — every request logged as structured JSON from day one, so any log aggregator can consume it later with zero rework. Bearer tokens are redacted.
3. **Security/access audit logging** — login success, login failure (with reason: unknown username, wrong password, archived account, no company access), and permission-denied rejections are now structured log events (`AuthService`, `PermissionGuard`). This is deliberately distinct from `TimelineEvent`: Timeline is business-entity history a company can see and act on; these are security/access events, a different concern that would pollute Timeline's purpose if merged into it (see `11-Database/Data_Model.md`'s implementation notes).
4. **Graceful shutdown** (`app.enableShutdownHooks()` in `main.ts`) — without this, a rolling deploy hard-kills in-flight requests instead of letting lifecycle hooks (Prisma disconnect, etc.) run first.
5. **Connection pool sizing guidance** (`.env.example`) — documented now, as a config habit, rather than discovered as a fire-fight once a second app instance exists.
6. **`TimelineEvent` ID strategy**: switched from client-generated UUIDv4 to UUIDv7 (time-ordered), generated in `TimelineService.record()`. This is the platform's highest-write-volume, longest-retention table ("millions of timeline events... years of history") — a random v4 primary key hurts B-tree insert locality now and blocks range-based partitioning later (the key carries no time signal). No schema/migration change was needed; only the generated value's shape changed. Deliberately **not** applied to other tables (Company/User/Asset/Operator/etc.) — no current benefit there, and would have been scope creep.
   - Implementation note: the `uuid` npm package's current major version is ESM-only and breaks under Jest's CommonJS transform (`SyntaxError: Unexpected token 'export'`) — found by running the test suite, not by review. Used the dedicated `uuidv7` package instead (zero dependencies, proper CommonJS `require` export), which is also simply a better-scoped dependency for a one-function need.

## Tier 1 — the seam exists, the infrastructure doesn't (yet)

| Concern | Chosen approach | Why this over the alternatives | Trigger to actually build it |
|---|---|---|---|
| Background jobs | `pg-boss` (Postgres-backed queue) | Jobs live in the database FleetOS already runs — no new stateful service (Redis, a broker) for a five-vehicle customer to indirectly pay for. BullMQ needs Redis; SQS is cloud-lock-in. When built, the worker runs as a separate process entrypoint from day one (even if co-deployed initially), so scaling workers independently later is a deploy-config change, not a rewrite. | First real async workload — email sending, report generation, future OCR/AI processing. |
| In-process domain events | `@nestjs/event-emitter`, emitted **after** a transaction commits | `TimelineService.record()` stays a direct, synchronous, same-transaction DB write regardless — that's correctness-critical (a mutation and its history entry must never diverge), not something to make async. | First real second consumer of a mutation (e.g. "notify on asset archive"). |
| Cursor (keyset) pagination | Stays offset-based (`page`/`pageSize`) for now | Switching before real data volume exists is optimizing before it hurts; a half-wired cursor field with no query behind it would be its own form of technical debt. See `12-API/API_Architecture.md`'s implementation notes for the documented migration path. | First tenant table exceeding ~100k rows per company, or a real slow-paging report. |
| `TimelineEvent` partitioning | Monthly range partitioning by `occurred_at` | Prisma migrations are plain SQL files, so adding `CREATE TABLE ... PARTITION OF ...` statements is additive when the time comes — no reason to pay the operational complexity before the row count justifies it. | Row count approaching tens of millions, or a measured query slowdown. |
| Connection pooling (PgBouncer) | Prefer a managed Postgres provider's built-in pooler over self-hosting PgBouncer | At one app instance this is a non-problem; don't add operational infra for a problem that doesn't exist yet. | Deploying a second concurrent app instance. |
| Metrics (Prometheus-compatible endpoint) | Deferred | No current dashboard/alerting consumer exists to make this actionable yet. | First production incident where real-time metrics would have mattered, or a first enterprise SLA. |
| Queryable security audit table | Promote Tier 0's structured log lines to a dedicated `SecurityAuditEvent` table (same RLS pattern as `TimelineEvent`) | Log-search is sufficient until someone needs to *query* audit history programmatically (e.g. for a compliance report). | First compliance/enterprise customer requiring queryable audit history, not just log search. |
| Feature flags | Per-company JSON settings column (no new service) | A real flag service (LaunchDarkly, self-hosted Unleash) is exactly the "infrastructure a small customer shouldn't pay for" this document exists to avoid defaulting into. | First genuine need for gradual or company-scoped feature rollout. |
| Service extraction ("every service scales independently") | Keep the modular monolith; module boundaries are already clean enough (only one documented cross-module dependency, `companies`→`auth`, for issuing a session token post-signup) to make extraction additive later | `02-Architecture/System_Architecture.md`'s existing reasoning already covers this: "splitting further than this at launch adds operational cost without a corresponding benefit for the initial customer size." Reaffirmed, not overridden. | OBD/CAN telemetry ingestion (`03-Hardware/OBD_CAN_Integration.md`) — already named in `System_Architecture.md`'s future-expansion notes alongside Fleet Intelligence/Sync — is the concrete trigger, because it's the one workload with fundamentally different scaling characteristics (high-frequency writes from thousands of vehicles) from request/response CRUD. |

## Load testing — findings (2026-07-22)

Commercial-launch readiness review (`00-Company/Commercial_Priority.md`'s "finish before deploying" default was explicitly superseded for this one pass, at founder direction, by the need to know the product won't fail under a paying customer's real traffic). Methodology: seeded a dedicated company (`apps/api/scripts/seed-load-test-data.ts` — 500 assets / 1,000 jobs / 400 maintenance jobs, npm run load-test:seed) and ran `apps/api/scripts/load-test.ts` (autocannon, 20-25 concurrent connections, 10-15s per endpoint, `npm run load-test`) against a locally-running instance backed by local Postgres. Absolute req/sec numbers are sandbox-specific (shared 4-vCPU box running Postgres, Node, and the load generator together) and should not be read as a production capacity figure — the relative findings and root causes are what matter.

**Finding 1 — Prisma's default connection pool (`num_cpus*2+1`, ~9) queues requests well before CPU or DB load is the real limiter.** At the default pool size, every list/report endpoint showed a large gap between p50 and p99 (e.g. `GET /v1/assets` p50=108ms but p99=1591ms) with zero actual errors — the classic signature of requests queued waiting for a pooled connection, not slow queries. Widening the pool via `connection_limit`/`pool_timeout` on the Prisma connection string closed that gap immediately (same endpoint: p50=82ms, p99=168ms) with no other change. **Fixed**: `infra/terraform/environments/base/main.tf`'s `db_urls` secret now sets `connection_limit=15&pool_timeout=20` on `app_database_url` (`connection_limit=5` on `auth_database_url`, used only at login/company-selection) — sized against `db.t4g.medium`'s ~450 `max_connections` so `api_max_task_count` (10) Fargate tasks can't collectively exhaust it. Re-check this sizing if `db_instance_class` or `api_max_task_count` change materially.

**Finding 2 — `GET /v1/fleet-health` throttled to a fraction of every other endpoint's throughput (~50 req/sec vs 150-290 elsewhere) for two compounding reasons, only one of which was a bug:**
- *A real inefficiency (fixed)*: the service ran two separate `hasPermission()` calls, each its own DB transaction, and made the main asset query wait for both to finish before it could even start (the query's `include` shape depended on the permission result). That's 3-4 sequential/serializing transactions for one HTTP request where every other endpoint needs 1-2. Fixed in `PermissionCheckerService`/`FleetHealthService`: a new `getGrantedKeys()` batches both permission checks into one query, and it now runs concurrently with the asset query (both relations are fetched unconditionally — cheap, small per-company tables — with permission still enforced at the point the data would otherwise reach the response: `computeMaintenanceFactor`/`computeComplianceFactor` return `not_permitted` and never surface the raw records). Verified this doesn't leak data across the permission boundary — the existing `not_permitted`-factor e2e test still passes.
- *A genuine scaling limit (not fixed, documented)*: `GET /v1/fleet-health` computes and returns a full per-factor breakdown for every asset in the company in one unpaginated response (171KB for 500 assets vs ~10KB for the equivalent assets list). Under concurrent load the API process pegged at ~140% CPU serving this endpoint alone — this is CPU-bound JSON serialization and per-asset scoring in Node's single event-loop thread, not something the connection-pool or query-shape fix above touches. **Trigger to actually fix**: a real customer's fleet size making this endpoint's latency user-visible (the fix is pagination or a summary-only default view, matching the same offset-pagination migration path already documented for other list endpoints above — not a redesign, an extension of a pattern already in place elsewhere in the API).

## Tier 2+ — deferred entirely, no code today
- **Distributed tracing (OpenTelemetry)** — real instrumentation cost for zero present value: no backend exists to send traces to, and structured logs plus request IDs are sufficient for a single monolith. Revisit once there are multiple services to trace a request across.
- **Microservice extraction / service mesh / container orchestration platform choice** — not before a Tier 1 extraction trigger fires.
- **Automated partition rotation tooling** (e.g. pg_partman) — defer until partitioning itself is live.
- **Offline-first sync engine build-out** — no DriverOS client exists yet to build it against; the API's data shape doesn't preclude it (`12-API/API_Architecture.md` already notes the batch/delta sync requirement).

## Acceptance criteria
- No enterprise requirement in the original review is met by an infrastructure component a five-vehicle customer's deployment actually has to run, unless that requirement is already satisfied by something FleetOS needs regardless (Postgres).
- Every Tier 1 item has a stated, concrete trigger — "later" is never open-ended.
- Adding a Tier 1 capability, when its trigger fires, should read as "add the planned piece," not "redesign around a decision made under the old assumption."
