# Universal Forms

## Purpose
Every transport business has paperwork beyond the standard checklist — incident reports, delivery exceptions, custom inspections, internal HR forms. Universal Forms turns any paper form into a digital one via a no-code, drag-and-drop builder, so companies aren't waiting on FleetOS engineering to support their specific paperwork.

## Requirements
- Drag-and-drop form builder in FleetOS (admin-permission gated) supporting common field types: text, number, single/multi-select, photo, signature, GPS location capture, date/time, linked-entity reference (e.g. "select asset," "select operator").
- Conditional logic (show/hide fields, branch to different follow-up fields) — the same underlying engine that powers Smart Checklists.
- Forms can be assigned to specific roles/contexts (operator-facing on DriverOS, office-facing on FleetHQ, or both).
- Submitted forms produce Timeline events on every entity they reference.

## Workflows
- Compliance officer builds a new "Incident Report" form in FleetHQ, referencing asset, operator, and location fields, with a conditional "injury involved" branch that requires additional detail and triggers a notification to a Safety Officer role.
- Operator completes the form on DriverOS (offline-capable); submission creates Timeline events on the asset and operator, and notifies whoever the template specifies.

## Edge cases
- Form template edited after submissions already exist: existing submissions retain the schema they were completed under; only new submissions use the updated template.
- Required linked-entity field where the entity doesn't sync locally yet (offline, new asset not yet cached): must gracefully allow completion with a placeholder that resolves on sync, not block the whole form.

## Technical considerations
- Shares its conditional-logic and offline-sync engine with Smart Checklists rather than duplicating it — these are the same underlying capability with different default templates and entry points.
- Form definitions and submissions are structured data (not just rendered PDFs), so submitted data is queryable and searchable (feeds Universal Search).

## Acceptance criteria
- A non-technical admin can build a new form with conditional logic and assign it to operators without engineering involvement.
- Submitted forms are fully searchable and produce correct Timeline events on every referenced entity.

## Future expansion notes
- A library of pre-built, Australia-specific form templates (e.g. standard incident report formats) is a reasonable pre-launch content investment, not a core engineering task.

## Implementation notes (v1, `apps/api` + `apps/fleethq` + `apps/driveros`)
- **Built**: `FormTemplate`/`FormSubmission` follow the exact versioned-template + immutable-snapshot pattern Smart Checklists already established — a template's `version` bumps only when its `fields` actually change (a rename doesn't bump it), and every submission carries its own `templateVersion` + full `templateSnapshot` so a later template edit never rewrites history. `FormTemplate.targetContext` (`DRIVER` / `OFFICE` / `BOTH`) drives which app offers the form. Submitting writes a Timeline event on the `FormSubmission` itself plus every distinct entity a `asset_ref`/`operator_ref` answer resolves to, satisfying "produce Timeline events on every entity they reference." Five granular permissions (`forms:view/create/edit/archive/submit`) — no hardcoded role check.
- **Field types**: `text`, `number`, `single_select`, `multi_select`, `date`, `asset_ref`, `operator_ref` are implemented and server-validated (a `single_select`/`multi_select` answer must be one of the template's own `options`; `asset_ref`/`operator_ref` must resolve to a real record in the submitting company). **`photo`, `signature`, and `GPS location capture` from the Requirements list are deliberately not built in this slice** — each is a materially larger feature (file/photo storage already exists for Glovebox/POD and could be wired in later; signature capture already exists for POD and is the obvious thing to reuse; GPS capture has no precedent anywhere in the app yet) rather than a same-shape addition to the field-type union.
- **Conditional logic**: single-level show/hide — a field's `showIfFieldId`/`showIfValue` gate its visibility on exactly one earlier field's answer (string equality, or "is one of the values" when the controlling field is a `multi_select`). This is the same engine Smart Checklists would use if it needed conditional items, per this doc's "shares its... engine" note — in practice that engine is this same minimal show/hide, not a richer branching tree. The Requirements' "branch to different follow-up fields" (i.e. a real decision tree, or the "injury involved" workflow-notification example) is not built.
- **Builder UI**: FleetHQ's `FormBuilderDialog` is add/remove/reorder-via-arrow-buttons, not literal drag-and-drop — the same scope call this codebase already made for Dispatch's stop reorder and Smart Checklists' item builder.
- **Office runner (FleetHQ)**: `FormRunnerDialog` fills in a template flagged `OFFICE` or `BOTH` — a "Fill in" action on each such row in the Forms templates table (gated on `forms:submit`), submitting through the same `POST /form-submissions` endpoint as DriverOS. It reuses the identical `showIf` visibility and required-field rules. Unlike DriverOS, `asset_ref`/`operator_ref` render as directory `Select` pickers (populated from `listAssets`/`listOperators`) because FleetHQ *does* have the full directory to browse — office staff aren't tied to a single job's asset. Previously an office-targeted template could be built but never filled in from anywhere; this closes that gap.
- **DriverOS**: `FormsPage` lists active DRIVER/BOTH templates and runs `FormRunner`, reachable both standalone from Today (general forms, e.g. an incident report filed anytime) and from a job via the same `?assetId=&assetName=` convention Checklist/Glovebox/Fault Reporting already use. Submission goes through the existing generic offline outbox (`queueMutation`/`drainOutbox`) with a client-generated id, so a lost-connectivity submit is queued and idempotently replayed exactly like a checklist or fault report — never silently dropped.
- **`asset_ref`/`operator_ref` on DriverOS have no search-and-select picker** — DriverOS has no general asset/operator directory to browse today, and typing a raw UUID would be unusable. Instead they resolve automatically: `operator_ref` always resolves to the operator filling the form in (self-reference is the overwhelmingly common case and needs no picker at all); `asset_ref` resolves to the job asset the form was opened from when reached via `?assetId=`, and otherwise shows "open this form from your current job" and blocks submit if the field is required. The Edge case's "required linked-entity field where the entity doesn't sync locally yet... must gracefully allow completion with a placeholder that resolves on sync" is consequently not applicable in this slice — there's no free-entry path to a not-yet-synced entity to begin with. A future increment could add a real searchable picker (backed by the same cached-template-list pattern Checklists already uses for offline asset lookups).
- **No IndexedDB draft-resume on DriverOS** — unlike `ChecklistRunner`, `FormRunner` keeps in-progress answers in React state only, not persisted across an app restart mid-fill. Checklists earned that persistence because a pre-start walk-around is answered item-by-item over several minutes outdoors; most forms are shorter and filled in one sitting. Flagged as a reasonable v1 cut, not an oversight — add it the same way Checklists did (a keyed IndexedDB store, saved on every answer change) if long forms turn out to need it.
- **Bug found and fixed along the way**: FleetHQ's shared `FormLabel` component requires `FormField`/`FormItem` context (it reads field state via `useFormField()`). Both the new `FormBuilderDialog` and the already-shipped `ChecklistTemplateFormDialog` used it as a bare section heading ("Fields" / "Checklist items") outside that context, which threw and crashed the whole dialog on open — a real, previously-undetected regression in the shipped Checklists builder, only caught by live-testing the new Forms builder in an actual browser. Fixed both by swapping to the plain `Label` primitive, which doesn't require field context.
- Live-tested end to end in a real browser (Playwright): built a form with text/single-select/conditional-text fields in FleetHQ, confirmed it rendered and saved; separately built and submitted a form exercising all seven field types from DriverOS (standalone and via job-context asset resolution), and confirmed the submission's answers — including the multi-select and the conditional field — round-tripped correctly via the API.
