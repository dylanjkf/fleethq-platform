# DriverOS — Overview

## Purpose
The in-asset tablet experience. Built for someone who is busy, sometimes offline, should never need a manual, and should never feel like they're using "enterprise software."

## Core screens/workflows (v1)
- **Login** — company-issued username and password (no NFC/QR/biometric in v1, per `CLAUDE.md` scope decision).
- **Today** — home screen showing today's job/route, replacing the old "what's next" phone call or SMS.
- **Pre-start / post-trip Checklist** — Smart Checklists (`01-Product/Smart_Checklists.md`).
- **Digital Glovebox** — view current asset's registration, insurance, roadworthy, emergency contacts.
- **Fault/Damage Reporting** — photo + note capture, feeding Workshop directly.
- **Messages** — chat with dispatch/office, replacing SMS.
- **AI Voice** — hands-free access to the above core actions.
- **Universal Search / Command Bar** — scoped to what's relevant to an operator's permissions.

## Requirements
- Full offline functionality for every workflow above; sync automatically and silently on reconnect, never requiring the operator to manage sync manually.
- Interface designed for glanceability and minimal taps — an operator should never need to dig through a menu tree to do the next thing (Product Philosophy's "build around the workday").
- Runs acceptably on modest, non-flagship Android tablets (per Hardware strategy — BYO tablets, no assumed high-end hardware).

## Edge cases
- Operator assigned to a different asset mid-shift (breakdown reassignment): Digital Glovebox, checklist state, and asset context must switch correctly and immediately, without residual data from the previous asset leaking into the new context.
- Low battery / interrupted session mid-checklist: in-progress data must persist locally and resume, never lost.

## Technical considerations
- Shares its offline sync engine with the rest of the platform (`02-Architecture/System_Architecture.md`) rather than implementing bespoke local storage/sync logic per screen.

## Acceptance criteria
- An operator with no prior training can complete a full day's core workflow (login, checklist, job visibility, fault report, messaging) without external help.
- Every core workflow functions correctly with zero connectivity from login to end of shift, syncing correctly once reconnected.

## Future expansion notes
- Operator-level Digital Glovebox (licence, medical, inductions) and operator gamification/safety scoring are reasonable next additions once the core workflow is proven in the field.

## Implementation notes
- **DriverOS v0 is now live** (`apps/driveros` — a second Vite + React + TypeScript SPA, same stack as FleetHQ to minimize context-switching, single dark-only theme, `min-h-14` touch targets, `user-select: none` + `touch-action: manipulation` for a tablet bolted in a vehicle). The v0 milestone shipped **Login**, **Today**, **Fault/Damage Reporting**, and (in the Digital Glovebox milestone) **Digital Glovebox** (view-only).
- **Every remaining v1 core screen has since shipped** (see this file's Core screens list and each feature's own doc): **Smart Checklists** (`apps/driveros/src/features/checklist`, offline-capable pre-start submission), **Messages** (`.../messages`, offline outbox), **Universal Forms** (`.../forms`, offline form runner), **AI Voice** (`.../voice`, hands-free command engine — `09-AI/AI_Voice.md`), plus **shift start/end**, **proof-of-delivery / multi-stop delivery** (`.../delivery`), a **notifications** center, and a **help/support** screen. The only Core-screens item not built as its own DriverOS surface is a dedicated Universal Search/Command bar (FleetHQ has one; DriverOS relies on the Today-centric flow instead). The frontend now also has its own automated test suite (Vitest — including the offline-DB and sync-engine tests `08-Compliance/Testing_Strategy.md` called for) and CI, added in the commercial-launch-readiness work.
- **Digital Glovebox is now a real DriverOS screen** (Digital Glovebox milestone): reached from Today via the current job's asset, showing registration/insurance/roadworthy status (reusing the already-built `ComplianceDocument` records, no new document model) plus a single free-text emergency contact (`Asset.emergencyContact`, editable from FleetHQ). See `01-Product/Digital_Glovebox.md`'s implementation notes for the full scoped-down slice (no file upload, no per-attached-unit support).
- **Login is company-issued username/password against the same auth endpoint FleetHQ uses** — no separate DriverOS auth path exists. This required resolving a foundational question first: an `Operator` record wasn't itself login-capable, so `Operator.userId` (nullable, unique, FK to `User.id`) now optionally links an Operator to a real `User` with a normal `CompanyMembership` + `Role`. Granting a DriverOS login is a FleetHQ Operators-tab action ("Link login", gated on `users:create`) that creates the `User` via the exact same path `POST /v1/users` uses — no parallel user-creation logic. `GET /v1/auth/me` now also returns the caller's linked `operator: { id, fullName } | null` so a DriverOS client can resolve "which Operator am I."
- **Today** shows the operator's currently assigned job(s) via `GET /v1/jobs?operatorId=&status=ASSIGNED`, each with a "Report a fault" action.
- **Fault/Damage Reporting is scoped to the asset from the operator's current job** (passed via URL query params from Today), not a general asset picker — photo capture is not in this slice (would need file-upload + storage, a separate decision). Submits to the existing `POST /v1/maintenance-jobs`, so a report appears in FleetHQ's Maintenance queue immediately, with no new backend concept introduced.
- **Offline-sync engine v0**: IndexedDB (`idb` package) with two stores — `outbox` (queued mutations) and `cache` (last-known-good reads). Fault report submission queues to the outbox immediately if `navigator.onLine` is false, or on a detected network failure; queued items replay in creation order on the next `online` event, stopping at the first failure rather than skipping ahead. Today's job list and the logged-in identity (`GET /v1/auth/me`) both fall back to their last cached value on a network failure, so a reload while offline does not log the operator out or blank the screen. **Deliberately no conflict resolution in v0** — every write in this slice is a create (a fault report), and the only read (the operator's own assigned job) isn't edited by the operator, so nothing can conflict yet. This will need real design once a workflow introduces edits to shared state (e.g. Smart Checklists).
- Verified end-to-end live: an Operator linked to a DriverOS login can log in, see their assigned job and asset, submit a fault report while online (confirmed as a real `MaintenanceJob` row visible in FleetHQ's Maintenance page), and submit one while offline (confirmed queued client-side, then confirmed synced automatically on reconnect with no user-initiated "sync" action).
- **Navigation hand-off + live location (courier vertical).** Two long-standing driver gaps closed together. (1) A stop's address was previously plain text — the driver had to retype it into their maps app. Today's next-stop card and the Record-delivery (`StopPage`) screen now show a **"Navigate to this stop ↗"** link (`src/lib/maps.ts` → the universal Google Maps directions URL) that opens the device's own maps app; DriverOS itself stays free of an embedded map/turn-by-turn (kept out of scope per `05-Dispatch/Dispatch_Overview.md`). (2) While on shift, the tablet reports its geolocation to `POST /v1/locations` on a ~45s heartbeat (`src/hooks/useLocationReporter.ts`) so the office can see it live. Entirely best-effort and non-blocking (CLAUDE.md "enhancements never block a core workflow"): it does nothing if geolocation is denied/unavailable or the context isn't secure, and is **not** queued to the offline outbox — a stale position replayed later would plot the driver where they used to be, worse than none.
- **PWA / installable + genuinely offline-loadable (commercial-launch-readiness).** The original offline story was only half-built: the IndexedDB outbox/cache made *data* survive offline, but the app itself couldn't *load* offline — the service worker only handled push, so nothing cached the app's own HTML/JS/CSS. An operator who closed the tablet and reopened it in a dead zone got a blank page, directly contradicting this doc's "every core workflow functions with zero connectivity" criterion. Fixed: `public/sw.js` now also caches the app shell (runtime caching — navigations network-first with a cached-shell fallback, static assets stale-while-revalidate, `/v1` and `/health` never cached since data offline behaviour is `offline-db.ts`'s job), registered on startup via `src/lib/register-sw.ts`. Added a `manifest.webmanifest` + real PNG icons + apple-touch-icon so DriverOS installs to the home screen as a standalone, full-screen app. **Verified in a real headless-Chromium run**: with the service worker controlling the page, a reload while offline no longer errors and the React app boots from cache (previously a blank page). Service workers only activate in a secure context (HTTPS or `localhost`), so on a plain-http LAN address this is a silent no-op — see `RUNNING.md` for how to test the PWA on a real tablet (localhost on the laptop, or the `npm run dev:lan` HTTPS mode + mkcert).
