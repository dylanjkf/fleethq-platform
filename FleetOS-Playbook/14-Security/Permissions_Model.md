# Modular Permissions & Custom Roles

## Purpose
Fixed roles (Operator, Dispatcher, Mechanic, Manager, Admin) force every company into the same operating shape. FleetOS instead gives every capability its own permission, and lets each company define roles that match how it actually operates.

## Requirements
- Every feature/action in the platform maps to an individually grantable permission (e.g., under Assets: View, Create, Edit, Archive; under Maintenance: View, Create, Schedule, Approve, Close; under Dispatch: Assign Jobs, Edit Routes, Cancel Jobs, Reallocate Work; under AI: View AI Insights, Create AI Reports, Run Fleet Analysis, Configure AI Automations; under Finance: View Costs, Export Reports, Manage Billing; under Compliance: View, Edit, Approve, Audit). Note there is no "Delete" action anywhere in this list — `11-Database/Data_Model.md`'s "no hard deletes on entities with Timeline/compliance relevance" constraint means the only destructive-sounding capability a role can grant is Archive.
- Roles are named bundles of permissions, fully editable and clonable by a company admin — never hardcoded in application logic.
- FleetOS ships default Role Templates (Operator, Senior Operator, Jockey, Dispatcher, Fleet Controller, Workshop Technician, Workshop Manager, Operations Manager, Compliance Officer, Safety Officer, Administrator, Finance, HR, Read Only, Custom) as a starting point companies can edit or clone, not a fixed set they're locked into.
- A user can belong to multiple companies with a different role (different permission set) in each, under one login (Multi-Company Support).

## Workflows
- Company admin clones the "Dispatcher" template, removes "Cancel Jobs," adds "View AI Insights," and names it "Junior Dispatcher" — no engineering involvement required.
- A contractor operator logs in once and sees a company switcher; selecting "ABC Logistics" gives them Dispatcher permissions there, selecting "XYZ Couriers" gives them Operator permissions there.

## Edge cases
- Permission changes affecting a currently-active session: must take effect promptly (not require a full re-login) for security-sensitive permission removals.
- A user with no permissions granted for a feature must see that feature absent from navigation, not visible-but-erroring.
- Role deletion where users are still assigned to it: must require reassignment before deletion, never leave a user with an undefined role.

## Technical considerations
- Permission checks happen at the API layer (per Core Principle "API-first" — every capability reachable through the same API a plugin would use), never only in UI rendering. UI hiding a button is not a substitute for the API rejecting an unauthorized call.
- This is the foundation Multi-Company Support and the eventual Open Platform / plugin marketplace both depend on — plugins will need to declare which permissions they require, following this same model.

## Acceptance criteria
- No feature in the product is gated by a hardcoded role check; all gating resolves through the permission system.
- A company admin can create a fully custom role from scratch and have it take effect without any engineering change.
- API calls are rejected server-side for any action the caller's permissions don't cover, regardless of what the UI shows.

## Future expansion notes
- Time-bound or context-bound permissions (e.g. a permission only active during a shift, or only for a specific asset/depot) are a plausible enterprise-tier extension once the core model is proven.

## Implementation notes (foundation milestone, `apps/api`)
- Permission keys follow a `resource:action` convention (e.g. `assets:create`) and live in one source-of-truth catalog (`src/common/permissions/permission-catalog.ts`) that both the seed script and the `@RequirePermission` guard reference, so a typo is a compile error rather than a silently-always-false check.
- A caller's permissions are resolved fresh from the database on every request — never embedded in the session JWT and never cached — specifically so the "must take effect promptly, not require a full re-login" edge case above actually holds: revoking a permission takes effect on the very next request.
- A permission-denied response uses the shape `{ "error": { "code": "FORBIDDEN", "message": "...", "requiredPermission": "assets:create" } }`, and every error response in the API (not only permission failures) shares the same `{ error: { code, message, ... } }` envelope — see `12-API/API_Architecture.md`'s implementation notes.
- `Role` and `Permission` are separate tables joined by `RolePermission`; `Role` is company-scoped (`company_id`) so "fully editable and clonable by a company admin" is a data fact, not just a UI affordance. `Permission` itself is a global, platform-defined catalog — companies choose which permissions a role includes, they don't invent new ones.
- Multi-Company Support (a user belonging to multiple companies with different roles) is modeled as `CompanyMembership` (User × Company × Role). A session JWT is scoped to exactly one `CompanyMembership` at a time, matching `12-API/API_Architecture.md`'s "a multi-company user's token is only ever valid for the company context it was issued for." Login returns a short-lived pre-auth token plus a company list when a user has more than one active membership, rather than requiring a separate "switch company" endpoint that re-authenticates from scratch.

## Implementation notes (Administration API milestone, `apps/api`)
- `POST /v1/roles`, `PATCH /v1/roles/:id`, `POST /v1/roles/:id/clone`, `POST /v1/roles/:id/archive` implement "roles are named bundles of permissions, fully editable and clonable" literally — cloning a template produces an ordinary custom role (`isSystemTemplate: false`), matching the "clones the Dispatcher template... names it Junior Dispatcher" workflow above. Templates aren't protected from editing or archiving — the spec explicitly says companies aren't locked into them.
- The "must require reassignment before deletion" edge case is enforced as a hard 409 (`ROLE_IN_USE`): archiving a role with any active `CompanyMembership` still pointing at it is rejected, naming how many users are affected, rather than silently leaving a membership pointing at an archived role.
- `POST /v1/companies` is self-service signup — it provisions a Company, an Administrator role (all permissions) and a Read Only role (all `:view` permissions) as starting templates, and the first admin User, in one atomic transaction, then logs that user in immediately. The same provisioning function backs `prisma/seed.ts`'s local dev bootstrap, so the two can't quietly diverge.
- `POST /v1/users` always creates a brand-new User — there's no flow yet for granting an *existing* user (one who already has a login elsewhere) access to a second company. The data model supports it (that's what CompanyMembership is for), but the discovery/invitation UX isn't specified anywhere, so it wasn't built speculatively.

## Implementation notes (enterprise readiness review, `apps/api`)
- Enterprise auth / future SSO: no code changed here, because `AuthService.issueSessionToken()` was already the single chokepoint every login path (username/password login, multi-company selection, post-signup auto-login) funnels through. A future SAML/OIDC identity provider integration is additive — a new strategy verifies identity, then calls this same method — not a rewrite of the session/permission model above. See `02-Architecture/Scaling_And_Enterprise_Readiness.md`.
- Permission-denied rejections are now also a structured security log event (`PermissionGuard`), distinct from and in addition to the 403 response itself — so "who was denied what, and when" is answerable from logs, not just from the caller's own error response.

## Implementation notes (Dispatch milestone, `apps/api` + `apps/fleethq`)
- Added `attached_units:view/create/edit/archive` and `dispatch:view/create/edit/assign/cancel` to the catalog — the latter maps directly onto this file's own Dispatch example list ("Assign Jobs, Edit Routes, Cancel Jobs, Reallocate Work"): `dispatch:assign` covers both "Assign Jobs" and "Reallocate Work" (the same action, initial vs. later), `dispatch:cancel` is literal, and `dispatch:edit` covers job-detail edits and marking a job complete (not separately named in this file, but consistent with the `resource:edit` convention every other resource uses). "Edit Routes" isn't implemented as its own permission yet since no Route entity exists.
- The `resource:action` key convention gained its first multi-word resource (`attached_units`), so the validating regex in `permission-catalog.spec.ts` was widened from single-word to snake_case resources — a test-convention fix, not a behavior change.
- Concrete illustration of "a permission revocation takes effect on the very next request, not after a re-login": this milestone's own two new permission categories were added to the platform-wide `Permission` catalog via a fresh `npm run seed`, but the FleetHQ Administrator role created *before* this migration didn't retroactively gain them (see `Backend.md`'s "seed-script permission drift" risk in the Memory Vault) — granting them required an explicit role edit through the Roles UI, exactly as the model intends: the platform never silently expands what a company's existing roles can do.

## Implementation notes (Workshop milestone, `apps/api` + `apps/fleethq`)
- Added `maintenance:view/create/edit/approve/close` to the catalog — maps onto this file's own Maintenance example list ("View, Create, Schedule, Approve, Close"): `maintenance:edit` covers both editing job details and the non-scheduling status transitions (no true proactive scheduling is built yet, see `06-Workshop/Workshop_Overview.md`), and `maintenance:approve`/`maintenance:close` are literal.
- Same seed-script permission drift observed again, exactly as predicted last milestone: the pre-existing Administrator role needed the five new Maintenance permissions granted through the Roles UI before the Maintenance nav item and Fleet page tabs appeared — confirms this is a recurring, expected step for every new permission category, not a one-off.
- **Multi-Company Support is now fully built**, not just designed-for: `POST /v1/users/link` grants an existing User (looked up by username via the same narrow `fleetos_auth` role login uses) access to a second company under a chosen role — the workflow this file's own example describes ("a contractor operator logs in once and sees a company switcher") is now real, verified end-to-end by linking one login to two companies with different roles in each and confirming the login response returns a `choose_company` list of both.

## Implementation notes (Compliance milestone, `apps/api` + `apps/fleethq`)
- Added `compliance:view/create/edit/archive` to the catalog. This file's own Compliance example list reads "View, Edit, Approve, Audit" — narrower than the `view/create/edit/archive` convention every other resource uses. `compliance:create` was added anyway (a document has to be logged before it can be viewed or edited, and the `resource:action` convention's own "no hard deletes, archive is the only destructive verb" rule needs `compliance:archive`). "Approve" and "Audit" aren't implemented as their own permissions in this slice: there's no approval workflow for a compliance document (unlike `MaintenanceJob`, which has one), and Timeline already provides audit visibility to anyone with `compliance:view` — a separate "Audit" permission would gate visibility into the same data twice for no real distinction yet.
- Seed-script permission drift recurred a third time, exactly as documented twice before: both companies' pre-existing Administrator roles needed `compliance:*` granted through the Roles UI (Acme) or a direct role update (Southern Star Logistics) before the Compliance nav item appeared — now unambiguously a permanent operational fact of this system, not a one-off worth re-litigating each milestone.

## Implementation notes (Import milestone, `apps/api` + `apps/fleethq`)
- No new permission category. Bulk CSV import (`01-Product/Onboarding_Import.md`) is gated on the pre-existing `assets:create`/`operators:create` permissions — it's a bulk *input method* for a capability that already exists, not a new one, so a company that has never granted `assets:create` shouldn't be able to bypass that by importing a CSV instead of clicking "New asset." This is the first milestone that deliberately introduces **no** new permission at all, which is itself worth noting: not every new capability needs its own grantable permission — only ones that grant genuinely new access.
- Because no new permission was added, the seed-script permission drift observed in the last three milestones doesn't apply here — every company that could already create Assets/Operators manually could immediately use the import feature too, with no Roles-UI step required. Concrete evidence that the drift is specifically a consequence of adding new permission categories, not a general property of shipping new FleetHQ features.

## Implementation notes (Fleet Health Score milestone, `apps/api` + `apps/fleethq`)
- Another milestone with no new permission category — `GET /v1/fleet-health` is gated on the pre-existing `assets:view`. But this one goes further than Import's "reuse an existing permission" pattern: the endpoint summarizes data from *two other* resources (Maintenance, Compliance) that each have their own view permission, and a caller granted `assets:view` alone has no standing claim to see either.
- New `PermissionCheckerService` (`src/common/permissions/permission-checker.service.ts`) extracts the exact permission-lookup query `PermissionGuard` already runs, as a small injectable service usable *inside* application logic rather than only at the route-gate level. `FleetHealthService` calls it once per factor (`maintenance:view`, `compliance:view`) and marks that factor `not_permitted` (with a zero deduction, not a guess) when the caller lacks it, rather than silently including data they couldn't otherwise see. This is a new, reusable pattern worth remembering for any future cross-resource rollup: gate the route on the "primary" resource's permission, then check secondary resources' permissions in-service before including their data.

## Implementation notes (DriverOS v0 milestone, `apps/api` + `apps/fleethq` + `apps/driveros`)
- No new permission category, and no new authentication mechanism. DriverOS login is the *same* login every FleetHQ user goes through — `AuthService.issueSessionToken()` remains the single chokepoint. What's new is `POST /v1/operators/:id/link-user`, gated on `users:create` (not `operators:edit`), since it genuinely creates a new login identity rather than editing an existing Operator record.
- `dispatch:view` and `maintenance:create` — both pre-existing permissions — are the only two a company needs to grant a "Driver" role for DriverOS's v0 slice (see jobs today, report a fault). This confirms the granular-permission design already scales down to an operator-facing client with zero new grantable capabilities, the same way Import and Fleet Health Score confirmed it scales across new office-facing features.

## Implementation notes (Digital Glovebox milestone, `apps/api` + `apps/driveros`)
- Another no-new-permission-category milestone — `GET /v1/assets/:id/glovebox` is gated on the pre-existing `assets:view` alone, with **no secondary `compliance:view` check**, unlike Fleet Health Score's cross-resource rollup. The difference: Fleet Health Score summarizes data across a caller's *entire* fleet (so a caller without `compliance:view` could otherwise learn fleet-wide compliance facts secondhand), while this endpoint is scoped to one specific asset the caller already holds `assets:view` for — the same "no extra check for your own assigned context" precedent Dispatch already established for a Job's nested Asset name. A "Driver" role now needs `assets:view` added (alongside `dispatch:view`/`maintenance:create`) for the Glovebox screen to work — the first DriverOS-relevant permission addition beyond the original two.
