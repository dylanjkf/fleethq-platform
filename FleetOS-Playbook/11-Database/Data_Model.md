# Database & Data Model — Overview

## Purpose
Define the core data modeling decisions that make "zero duplicate data," "everything has a timeline," and Fleet Graph queries all practically achievable.

## Core entities (v1)
Company, User, Role, Permission, AssetClass, Asset, AttachedUnit, Operator, Customer, Depot, Job, Delivery, Route, MaintenanceRecord, FaultCode, ServiceHistoryEntry, ComplianceDocument (registration, insurance, roadworthy, etc.), Form, FormSubmission, Checklist, ChecklistSubmission, FuelRecord, TimelineEvent, GraphRelationship, Attachment/Photo, Message, AIConversation.

`AssetClass` is a small, mostly-static reference entity (Land, Air, Sea — only Land populated with real behavior at launch) that every `Asset` references, per `02-Architecture/Asset_Class_Model.md`'s requirement that "every Asset belongs to exactly one Asset Class." Compliance and fatigue rule resolution take both `AssetClass` and `jurisdiction` as inputs, never jurisdiction alone.

## Modeling approach
- **Primary store**: a relational database (strong consistency, mature tooling, well understood at the team's likely skill level) holds core entity records.
- **Event/Timeline layer**: append-only `TimelineEvent` records, each referencing the entity(ies) involved, an event type, a timestamp, and the actor (human or automation) responsible. Entity state changes are always accompanied by a TimelineEvent — this is a discipline enforced at the service layer, not left to be remembered per-feature.
- **Graph relationships**: modeled as a dedicated `GraphRelationship` table/structure (source entity, target entity, relationship type, valid-from, valid-to) rather than ad hoc foreign keys scattered per feature. Multi-hop queries are built on top of this structure; if query performance at scale requires it, a dedicated graph database can be introduced later as a read-optimized projection without changing the source of truth.
- **Multi-tenancy**: every table that holds company-scoped data carries a `company_id`, enforced via row-level access control at the data layer, not solely application-layer filtering.

## Non-negotiable constraints
- No hard deletes on entities with Timeline/compliance relevance — archiving (soft delete with a status flag) preserves history, per "everything has a timeline."
- No entity is ever silently mutated without a corresponding TimelineEvent.
- Schema must support a `jurisdiction` concept on compliance-relevant tables from day one, even though only "Australia" is populated at launch.

## Edge cases
- High write volume from OBD telemetry: telemetry data is high-frequency and different in shape from core business entities — it should be modeled and stored separately from the core relational entities (e.g. a time-series-appropriate store), summarized/aggregated into Timeline events rather than every raw reading becoming a Timeline entry.
- Schema evolution: migrations must never silently drop historical data; column/field deprecation follows an additive-then-remove pattern with a defined deprecation window.

## Acceptance criteria
- Every entity mutation is traceable to a TimelineEvent.
- Multi-hop Fleet Graph queries (per `01-Product/Fleet_Graph.md` acceptance criteria) return correct results against the modeled `GraphRelationship` structure.
- No tenant's data is queryable by another tenant under normal data-layer access.

## Future expansion notes
- If multi-hop graph queries become a performance bottleneck at large scale, introducing a dedicated graph database as a synchronized read model (not a replacement source of truth) is the anticipated evolution path — this is intentionally deferred rather than adopted preemptively.

## Implementation notes (foundation milestone, `apps/api`)
- "Row-level access control at the data layer" is implemented as real Postgres row-level security, not an ORM-level convention: a dedicated low-privilege `fleetos_app` database role (no `BYPASSRLS`, not the table owner) is what the running API connects as, and every company-scoped table has a policy keyed on a `app.current_company_id` session setting the app sets per request. The schema-owning role used by `prisma migrate` bypasses RLS, same as any Postgres superuser/owner would — that's expected, since it's only ever used for migrations, not request handling. See `prisma/migrations/*_row_level_security/migration.sql` in `apps/api`.
- `Role` (per `14-Security/Permissions_Model.md`) is company-scoped and joined to the global `Permission` catalog through a `RolePermission` table; Multi-Company Support is a `CompanyMembership` join of User × Company × Role. Neither is named explicitly in this file's entity list above because they're the implementation of "Role" and "a user can belong to multiple companies," not new product concepts.
- `AssetClass` carries an `isImplemented` flag (true only for `LAND` at launch) so "only Land Asset Class behavior is implemented right now" (`CLAUDE.md`) is something the API can check and reject against, not just a build-time omission — creating an Asset against an unimplemented Asset Class is a validation error, not silently-accepted dead data.
- Resolved (Administration API milestone): `User` now has row-level security too, scoped by "shares an active-or-archived CompanyMembership with the requesting company" rather than a `company_id` column (it doesn't have one — a User is intentionally cross-company). One narrow exception remains: login's initial username lookup happens before any company or user context exists, so it runs through a second, even-more-restricted runtime role (`fleetos_auth` — BYPASSRLS, but granted `SELECT` on `users` and nothing else) rather than the normal tenant-scoped connection. See `prisma/migrations/20260713080000_admin_entities_and_users_rls/`.
- Postgres/Prisma gotcha worth knowing before adding a new RLS-protected table: `INSERT ... RETURNING` and `UPDATE ... RETURNING` (what Prisma's `.create()`/`.update()` always generate) re-check SELECT visibility on the row being returned, not just the WITH CHECK expression governing the write itself. This broke two things here: creating a User before their CompanyMembership exists (fixed by generating the id client-side and using `createMany`, which has no RETURNING), and archiving a user's last membership then trying to read them back in the same response (fixed by not requiring the membership to still be active in the users policy). See `prisma/migrations/20260713081500_fix_users_rls_visible_when_archived/`.
- Resolved (Dispatch milestone): `AttachedUnit` now has a full CRUD API resource (mirrors Asset/Operator exactly). `GraphRelationship` now has its first real write path — assigning a Job to both an Asset and an Operator opens a timed `OPERATED` relationship; completing, cancelling, or reassigning the job closes it. See `05-Dispatch/Dispatch_Overview.md`'s implementation notes for the full scoped-down slice and what's still deliberately not built (live map/GPS, OBD-derived status, route optimization, chat, and `AttachedUnit`-to-`Asset` `PAIRED_WITH` pairing).
- New entity: `Job` (per this file's core entity list) — scoped to what the Dispatch milestone actually needed: title/description, optional `assetId`/`operatorId`, a `JobStatus` enum (`UNASSIGNED`/`ASSIGNED`/`COMPLETED`/`CANCELLED`). Deliberately has no `archivedAt` — unlike Asset/Operator/AttachedUnit, a Job's terminal states (`COMPLETED`/`CANCELLED`) are themselves the "no hard delete" mechanism; every Job stays permanently visible in its final state rather than needing a separate archive flag. `Customer`, `Depot`, `Delivery`, and `Route` (also named in this file's core entity list) are not modeled yet — out of scope for this slice, see the Dispatch doc.
- New entity: `MaintenanceJob` (Workshop milestone) — an Asset (required), title/description, `MaintenanceSeverity` (Normal/Critical), a linear `MaintenanceJobStatus` (Open/In Progress/Parts Pending/Complete), an optional `reportedByOperatorId`, `resolutionNotes`, and `approvedAt`/`approvedByUserId`. Same "terminal status is the no-hard-delete mechanism" pattern as `Job` — no `archivedAt`. `MaintenanceRecord`, `FaultCode`, and `ServiceHistoryEntry` (named in this file's core entity list) are not modeled as separate entities yet — this milestone's `MaintenanceJob` covers the same ground at a scope appropriate for manual logging; splitting them out is a natural move once Smart Checklist/OBD-sourced data actually needs the distinction. See `06-Workshop/Workshop_Overview.md`'s implementation notes.
- Multi-Company Support's other half is now built (Workshop milestone): `POST /v1/users/link` grants an *existing* User access to a second company by username, reusing the same narrow `fleetos_auth` lookup pattern as login's pre-context username lookup (see above) — necessary because, by definition, no shared CompanyMembership exists yet between the requesting company and the user being looked up. A unique constraint on `(userId, companyId)` means a previously-deactivated membership is reactivated rather than re-inserted.
- New entity: `ComplianceDocument` (Compliance milestone) — an Asset (required), `ComplianceDocumentType` (Registration/Insurance/Roadworthy), optional document number, optional `issuedAt`, required `expiresAt`, a `jurisdiction` string (defaulting `"AU"`, per this file's own "jurisdiction concept on compliance-relevant tables from day one" constraint), and optional notes. Unlike `Job`/`MaintenanceJob`, this entity uses the `archivedAt` reference-record pattern (same as Asset/Operator/AttachedUnit) rather than a terminal-status pattern — a compliance document has no natural terminal lifecycle (renewal means logging a new row, not mutating the expired one), so `archivedAt` here means "this record was a mistake," not "this record reached its end state." Expiry status (valid/expiring soon/expired) is computed at read time from `expiresAt`, never stored — a second, derived-and-cached status column would violate "zero duplicate data entry" for no benefit. `MaintenanceRecord`, `FaultCode`, and `ServiceHistoryEntry` remain unmodeled (see Workshop's own note above); `ComplianceDocument` doesn't cover them either — it's scoped to registration/insurance/roadworthy currency only, per `08-Compliance/Australian_Compliance.md`'s implementation notes.
- No new entity for the Import milestone (`01-Product/Onboarding_Import.md`) — bulk CSV import is a new write *path* onto `Asset`/`Operator`, not a new table. `ImportsService` calls `AssetsService.create()`/`OperatorsService.create()` directly per row rather than duplicating their validation or Timeline-recording logic, so an imported record and a manually-entered one are indistinguishable afterward (same columns, same RLS policy, same Timeline "created" event). This is also why no new permission category was introduced — see `14-Security/Permissions_Model.md`'s implementation notes.
- No new entity for Fleet Health Score either (`01-Product/Fleet_Health_Score.md`) — it's a pure read-model computation over `Asset`, `MaintenanceJob`, and `ComplianceDocument`, with no write path and nothing stored. The score and its factor breakdown are derived fresh on every `GET /v1/fleet-health` call, same reasoning as Compliance's own expiry status: a cached/stored score would drift from the data it's summarizing the moment a Maintenance job or Compliance document changed underneath it.
- Postgres gotcha worth knowing before writing a new RLS policy: `current_setting('app.x', true)` only returns true `NULL` if `app.x` was *never* referenced on that database connection. A connection-pooled app (Prisma, same as any other pool) reuses connections across unrelated requests, so once any request has set a session GUC via `SET LOCAL`-style `set_config(..., true)`, later requests that reuse that same pooled connection see it reset to an *empty string*, not `NULL`, once their own transaction ends — and casting `''::uuid` errors rather than behaving like "unset." Every policy in this codebase reads session GUCs through `NULLIF(current_setting(...), '')::uuid` for exactly this reason; found by actually running the integration tests against a real Postgres, not by review.
- `TimelineEvent` rows now get an explicit client-generated UUIDv7 (time-ordered) id, not the schema's default UUIDv4, generated in `TimelineService.record()`. This table is explicitly the highest-write-volume, longest-retention one in the platform, and a random v4 id hurts B-tree insert locality now and would block range-based partitioning later (the id carries no time signal). No schema/migration change needed — the column stays a plain Postgres `uuid`. Not applied to other tables; see `02-Architecture/Scaling_And_Enterprise_Readiness.md` for the full reasoning and the partitioning trigger (row count approaching tens of millions, or a measured slowdown).
- Comprehensive audit logging deliberately does **not** mean everything security-relevant becomes a `TimelineEvent`. Login attempts (success/failure/reason) and permission-denied rejections are structured application log events instead — Timeline is business-entity history a company can see and act on; access/security history is a different concern with a different audience, and merging the two would pollute Timeline's purpose. See `02-Architecture/Scaling_And_Enterprise_Readiness.md` for when this gets promoted to a dedicated queryable table.
- New relation (DriverOS v0 milestone): `Operator.userId` (nullable, unique, FK to `User.id`, `ON DELETE SET NULL`) optionally links an Operator to a real login-capable `User`. An Operator is a fleet-registry record (name/contact/jobs/maintenance reports); it only becomes login-capable once linked to a `User` that itself has a normal `CompanyMembership` + `Role`, same as any FleetHQ user — there is no separate Operator-authentication mechanism. Linking is done via `POST /v1/operators/:id/link-user`, which delegates to the exact same `UsersService.create()` path `POST /v1/users` uses (reusing the Operator's existing `fullName` rather than asking for it again), then records a `login_linked` Timeline event on the Operator. `GET /v1/auth/me` now also resolves and returns the caller's linked `operator: { id, fullName } | null`. See `04-DriverOS/DriverOS_Overview.md`'s implementation notes.
- New column (Digital Glovebox milestone): `Asset.emergencyContact` (nullable free-text). No new entity — the full Digital Glovebox spec's document store (registration/insurance/roadworthy as files) is out of scope for this slice; that status is served straight from the already-modeled `ComplianceDocument` records instead, reusing `ComplianceService`'s existing expiry-status computation rather than a parallel one. `GET /v1/assets/:id/glovebox` (new) returns both together for DriverOS's Digital Glovebox screen. See `01-Product/Digital_Glovebox.md`'s implementation notes.
